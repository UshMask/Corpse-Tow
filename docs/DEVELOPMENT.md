Повседневные действия — в [Мод.cmd](../Мод.cmd), поведение и данные —

## Рабочий процесс через меню

Номера доступных команд сохранены; F — быстрый запуск актуального кода. `H` открывает это руководство, `D` — дашборд на 4180
(его сервер и наблюдатель должны уже работать). Меню не публикует мод и не обновляет сервер.

| Цель | Порядок | Что получаем |
|---|---|---|
| Проверить небольшую правку | Целевые тесты ниже → 1 | Проверка логики без игры; полный набор не обязателен |
| Собрать Java | 2 | Новый JAR в исходниках; установка и игра не запускаются |
| Проверить руками | Закрыть тестовый клиент → F | Сборка JAR, тестовая установка, загрузка сохранённого `PZT_VehicleLab`; мир не сбрасывается |
| Измерить текущий FPS | 9; не управлять тестовым клиентом | Отдельный снимок кода, 32 тела, прогрев 10 с + замер 10 с, вывод FPS, закрытие клиента |
| Разобраться в установке | 6 | Сравнение профиля разработки и проверка актуальности сборки и тестов |
| Другой профиль разработки | 3 | Установка и запуск `local/client`; это не полигон пункта 7 |
| Обычная игра | 4 | Steam-профиль; не локальный кандидат |
| Готовить выпуск | 8 → 2 → сверка кандидата → SP/MP-приёмка | Полный набор проверок, затем пакет и отдельная процедура публикации |

F использует тот же сценарий, что 7 → 2: без PZO, с Viewpoint, без автоматических тестов.
В подменю 7, 9 и M ноль возвращает к главному меню. Пункт 3 сам Java не
пересобирает: после правки Java сначала выполните пункт 2.
Пункт 7 сохраняет варианты PZO/Horse для проверки совместимости. Для проверки самого
мода выбирайте вариант 2 без PZO. Подпункт 4 — автоматическая проверка поведения,
а не замена FPS-пункту 9. Ручную сцену и измерительную сцену не смешиваем.
Пункт 9 добавляет завершённый результат в журнал; наблюдатель обновляет дашборд.
Дата, версия и SHA-256 комплекта сохраняются рядом с результатом. Старые прогоны остаются.

### Что намеренно не помещено в главное меню

- `performance_compare.py` — сравнение двух конкретных снимков; нужны пути и одинаковый протокол.
- `performance_series.py` — матрицы 0/1/8/32, настройки, диагностика CPU/GC/JIT; параметры выбираются под вопрос исследования.
- `acceptance_run.py`, `tools/mp-test/` — приёмка и MP-стенд, отдельные от FPS сценарии.
- `Restore-ManualWorld.py`, `Restore-Snapshot.ps1` — восстановление с резервной копией; не скрытый шаг обычного запуска.
- `build_test_map.py` — изменение карты, а не обязательная подготовка каждого замера.
- `benchmark_*` и `cvp_agent.py` — нижний уровень сценариев/моста; не дублирующие кнопки для пользователя.

Восстановление исходной сцены доступно в пункте 7 → 5. Оно использует явно
заданный профиль Codex и сохраняет предыдущий мир; обычное продолжение — 7 → 2.

## Кто запускает и когда

По умолчанию агент после правки запускает целевые логические тесты, расширяя их
по рискам. Игра, профилирование, сброс сцены, сервер и публикация запускаются только
в рамках явно согласованной задачи, а не как скрытая часть обычной проверки.

| Этап | Автоматическая работа агента | Ручная оценка пользователя |
|---|---|---|
| Правка Lua | Целевые SP/MP-тесты затронутого контракта | Не обязательна для внутренних изменений |
| Правка Java/рендера | Сборка, native-проверки, согласованность Lua/JAR | Туман, Viewpoint, плавность после установки кандидата |
| Проверка поведения | Приёмочный сценарий, отмена, сохранение/загрузка, возврат вещей | Меню, удобство, ощущение сопротивления |
| FPS | Замороженный снимок, одинаковая карта, камера и настройки. Для удалённой серии используйте [GPU-стенд immers.cloud](REMOTE_BENCHMARKS.md) | Пункт 9 для быстрого локального ориентира. Клиентом во время замера не управлять |
| Поиск затрат | Отдельная диагностическая серия Lua/Java/CPU/GC/JIT | Просмотр профилей в дашборде; её FPS не смешивать с обычными замерами |
| Перед выпуском | Полный check, сборка кандидата, проверка обновления и SP/MP по рискам, пакет/changelog | Визуальная приёмка кандидата |
| Публикация | Только по запросу: публикация и сверка скачанных файлов с пакетом | Сервер обновляется отдельным согласованным действием |

Короткий FPS не является проверкой корректности или обязательным этапом каждой
правки. Перед выпуском важнее отсутствие регрессий, согласованность комплекта и
сохранность вещей; сравнение производительности нужно при соответствующих изменениях.

## Единая карта, раздельные сохранения

Стандарт новых SP-проверок — длинная прямая **2400 клеток**, исходная геометрия
`tools/pz-test/map/42/media/maps/PZT_LongProvingGround`. `Quick-Test.ps1` уже выбирает
её по умолчанию. В установленном профиле она называется `PZT_ProvingGround`:
это сохранённый ID карты, а не признак короткой дороги. Лаунчер устанавливает ровно
одну выбранную геометрию и убирает дублирующий каталог карты в резервную копию.

Ручной пункт 7, FPS-пункт 9 и короткий сценарий 7→4 используют `PZT_VehicleLab`
и этот лаунчер. Сохранения при этом разные: ручной профиль `CorpseTowQuickTest`,
автоматические `CorpseTowPerf-On/Off`. Эталон `local/test-worlds/performance-32-v2`
содержит сцену, а не альтернативный генератор карты. Ручное сохранение нельзя
использовать как источник следующего автоматического замера.

Старые пути ещё существуют: `CVP_QuickTest` и `benchmark_world.py` относятся к
прежним сценариям; старое имя мира доступно только через явный параметр.
Новые команды должны явно передавать `-WorldName PZT_VehicleLab`. Короткая карта
240 доступна только для исторических A/B по `-RoadLength 240`; не использовать её
для новых обычных замеров. Генератор карты отдельно по умолчанию строит
2400, поэтому вызывать его с явным `--road-length 2400`.

Единая геометрия не означает единый изменяемый мир. Нельзя подменять сохранения
при работающем клиенте; после изменения геометрии уже сохранённые клетки могут
содержать старое состояние. Для воспроизводимого замера нужны эталон сцены и
отпечаток установленной карты. В performance_series проверка хешей карты и числа
заголовков включена по умолчанию (`--road-length 2400`): для контролируемых
серий передавать `--road-length 2400`. Состояние карты удалённого MP-стенда следует
сверять отдельно; локальный исходник не доказывает, что сервер загрузил его.

Реализованы выбор 0/1/8/32 в FPS-подменю и обязательная запись карты в новых сериях.
Восстановление ручного мира с выбором профиля доступно отдельно — пункт 7 → 5
(см. ниже); это не скрытый шаг обычного запуска.

## Окружение

Пути к игре, JDK, ZombieBuddy и Viewpoint задаются в `local/settings.json`.
Без файла используются библиотеки Steam, локальный JDK и `JAVA_HOME`.
Параметры `-Game`, `-Jdk`, `-ZombieBuddy`, `-ViewpointJar` имеют приоритет.

Python 3.11 и Lupa с Lua 5.1:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-test.txt
```

Обычным Python/Lua-тестам игра и JDK не нужны. Для нативных проверок нужны
установленные PZ B42.21, JDK 25, ZombieBuddy, Viewpoint и доступный OpenGL-драйвер.
Настройки, тестовые профили и журналы в `local/` не входят в Git.

## Проверки

Состояние на 09.11.2026: 0.8.0 опубликована, основной сервер не обновлялся.
BodySpread-подслучаи закрыты как устаревшая тест-модель (production не менялся,
`test_body_spread.py` — 14 тестов OK); ограничение выше ~40–45 м/с записано, но не
исправлялось. Перед общим прогоном фиксируйте точный снимок кода (коммит/хеши) и не
меняйте файлы во время проверки: `Source changed during checks` означает, что
результат не засчитан. Целевые и общий прогоны снимка
`3716f9f` и их журналы — в `local/runs/final-20261109/`; полный прогон не заменяет
живую игру, WAN и проверку основного сервера.

```powershell
powershell -NoProfile -File tools/Project.ps1 -Action test
powershell -NoProfile -File tools/Project.ps1 -Action check
powershell -NoProfile -File tools/Project.ps1 -Action diagnostics
```

- `test` — общий Python/Lua-набор; это действие по умолчанию и пункт 1 меню.
  Он исключает только несколько долгих матриц из полного Python/Lua-набора,
  поэтому для небольшой правки используйте целевые тесты ниже.
- `check` — полный Python/Lua-набор, игровой компилятор Kahlua и Java/native-проверки;
  пункт 8. Он не заменяет JAR и не устанавливает мод.
- `diagnostics` — состояние локальной установки, актуальность проверок и сборки;
  пункт 6. Номер версии и совпадение файлов не доказывают версию уже открытой игры.

Полный Python/Lua без Java: `.venv/Scripts/python.exe -B tools/run_tests.py --full`.
Отдельные тесты: `.venv/Scripts/python.exe -B -m unittest discover -s tests -p "test_link_graph.py"`.
Для обычной оптимизации используйте целевые проверки `.venv/Scripts/python.exe -B tools/test_optimization.py`.
После небольшой правки сначала выбирайте тесты затронутого поведения; FPS-замер
нужен, когда изменение должно влиять на производительность. Полный прогон — для
предрелизного кандидата и когда масштаб или риск изменения его оправдывают.

Результаты и контрольные суммы сохраняются в `local/latest-*.json` и `local/runs/`.
Быстрый отчёт не заменяет полный. При параллельных правках проверяйте неизменяемый
снимок; `Source changed during checks` означает, что проверка не засчитана.

Выбор проверки по изменению:

| Изменение | Первая проверка | Когда расширять |
|---|---|---|
| Меню или текст | Тесты затронутого меню/локализации | Ручная проверка при изменении поведения интерфейса |
| Граф связей, физика или сопротивление | Тесты затронутых модулей; `test_optimization.py` для нескольких смежных модулей | Native и изолированный игровой сценарий, если затронуты движок или производительность |
| Предметы, сохранение, отмена, сетевой протокол | Целевые тесты соответствующего контракта, включая ошибки и восстановление | Настоящее сохранение/перезапуск и SP/MP по затронутому сценарию |
| Оптимизация FPS | Целевые тесты поведения, затем при необходимости короткая A/B-пара на 32 телах | Повтор в обратном порядке или длиннее при неоднозначности; отдельные сценарии для масштабирования |
| Предрелизный кандидат | Неизменяемый снимок, полный `check`, сборка и сверка JAR | Игровая и MP-приёмка по изменённым рискам, сохранения и пакет |

Проверка одного уровня не заменяет другой. Не удаляйте тест только из-за числа
проверок или совпадения названий: сначала подтвердите, что он дублирует тот же
контракт, а не отдельный случай отказа. Детали внутренней реализации проверяйте
только если они действительно являются требованием (например, запрет дорогой
операции на горячем пути); во всех остальных случаях предпочитайте результат.

Тесты защищают сохранность тел, лута и оборудования, отмену действий, полномочия
сервера, совместимость сохранений и устойчивость движения. Не закрепляйте в них
случайные детали реализации вместо поведения. Импорт теста не должен запускать сценарий.
`tests/fixtures/v031/` — исторические фикстуры совместимости, не текущий игровой контроллер.
Модель мира создаёт `lua_fixture.create_world`, текущие модули загружает
`create_current_fixture`. Старый контроллер подключается явно через
`legacy_fixture.create_legacy_fixture`; генератор старых сохранений — только в
миграционных тестах. Обычные SP/MP-тесты не читают архив v031 и не подменяют меню.
Удалённые chainSize/updateBindings/endTail лежат в v031/*_operations.lua:
исторический загрузчик вставляет их в исходную область локальных переменных.
Игровые модули и современные фикстуры их не загружают; тесты старых операций
оборудования явно используют vm(legacy=True).

Модели Lua, Java/native-проверки и настоящая игра — разные уровни доказательств.
Проверка очереди импульсов без мира не подтверждает Bullet или живую MP-сеть;
скрытый OpenGL-тест не подтверждает вид игры. Для SP/MP используйте существующие
сценарии и мост на копии мира; игровые действия проходят меню и штатную очередь,
а не прямой вызов `perform`. Проверка SP не заменяет двух настоящих MP-клиентов.

## Сборка и локальный запуск

```powershell
powershell -NoProfile -File tools/Project.ps1 -Action build
```

Поддержка Viewpoint встроена в основной `CorpseProxyWorld.jar` и включается только
при наличии Viewpoint. На выделенном сервере интеграция не запускается.
`CorpseProxyViewpoint` сохраняет прежний ID без Java-кода. Флаг `-Viewpoint`
принимается для старых скриптов и больше не меняет состав сборки.

Пункт 3 устанавливает копию из проекта в `local/client/mods/CorpseProxyLab`,
сохраняя предыдущую установку в `backups/local-install-*`. Профиль разработки
использует `local/client` и приоритет `mods,steam`. Рабочий источник — проект;
установленную копию вручную не редактируем.

Пункт 4 открывает обычный Steam-профиль. Старые копии в `Zomboid/mods` и
`Zomboid/Workshop` могут перехватить подписку; лаунчер требует сначала убрать их.
Перед заменой Java или сменой профиля полностью закройте игру. Доверие ZombieBuddy
к изменившемуся JAR подтверждается вручную.

Пункт 7 и `tools/Quick-Test.ps1` используют отдельный тестовый профиль.
Варианты Viewpoint/PZO/Horse, подготовка полигонов, режим без звука и сценарии
приёмки описаны в [руководстве стенда](../tools/quick-test/README.md).
Обычные сохранения пользователя не подменяем тестовыми мирами.

Для сохранённого полигона явно указывайте мир: значение по умолчанию
`CVP_QuickTest` может содержать другую, старую сцену.

```powershell
powershell -NoProfile -File tools/Quick-Test.ps1 -WorldName PZT_VehicleLab -ReuseAssets
```

Команда использует существующее сохранение, но не гарантирует наличие 32 тел:
состав сцены проверяется после загрузки через мост. Перед восстановлением или
заменой мира сохраняйте его резервную копию при закрытом клиенте.

## Производительность

Для повторных замеров на отдельной машине используйте [GPU-стенд immers.cloud](REMOTE_BENCHMARKS.md). На нём доступны стандартный SP, сравнение сборок и MP с сервером и двумя клиентами на одной ВМ. Показатели сравнивайте с сохранённой базой того же стенда и протокола. Результаты облачных прогонов доступны в [дашборде](../local/performance-cloud/index.html).

Для быстрого отбора оптимизации используйте одну пару 32 тела A→B через
`performance_compare.py --preset express`; при неоднозначности повторите B→A.
Это скрининг, а две пары не определяют точную погрешность; для подтверждения
нужны дополнительные повторы и контроль условий. Матрица количеств не обязательна
для каждой правки, но нужна, если вопрос касается масштабирования или первой связи.

Для исследования постоянных затрат различать три состояния: мод выключен,
мод включён без связей, первая активная связь. Затем отдельно проверять рост
нагрузки. Сохранять одинаковое окружение и учитывать стоимость движения/отрисовки
тела самим движком. Сравнивать миллисекунды кадра наряду с FPS; короткий express
не доказывает устойчивый выигрыш. Фокус, прогрев и фон записывать в ограничения.
Кандидаты оптимизации и их условия перечислены в
[отложенных исследованиях](../ROADMAP.md#4-отложенные-исследования).

Браузерные результаты RopeSandbox не подтверждают физику, FPS или визуал PZ.
Замеры входа PZJoinLab отделять от игровых замеров Corpse Tow; повторный вход
без ускорителя нужен, чтобы отличить работу прототипа от прогрева файлового кэша.

[Единый журнал](../local/performance/index.html) открывает принятые результаты,
диагностику и исторические страницы. Пересобрать его без запуска игры:
`python tools/performance_journal.py`.

Повторы одной сборки — `tools/performance_series.py`; сравнение двух сборок —
`tools/performance_compare.py`; отдельные запуски с модом и без него —
`tools/performance_run.py`; сохранение/перезапуск — `tools/acceptance_run.py`.
У серии есть `--mode fps` (по умолчанию), `diagnostic` и `acceptance`:
повторы одной сборки идут в одном клиенте; 15-секундная проверка остановки — только
в `acceptance`. Возврат исходных верёвок и восстановление сцены обязательны всегда.
Сравнение двух готовых сборок: `tools/performance_compare.py --before OLD --after . --repeats 3 --output local/runs/NAME-ab`.
Каждая сборка фиксируется отдельно; повторы идут в одном клиенте, между сборками — перезапуск.
FPS-серия запускается без Lua debug; JFR включается отдельным `--jfr`, без Lua-обёрток.
По умолчанию `--preset fast`: один прогрев на клиент, запись 10 секунд, два повтора.
`--preset full`: на каждой поездке прогрев 10 секунд и запись 20 секунд, три повтора.
`express`: прогрев 1 с, запись 3 с, один повтор; доступен для FPS-серии и
предварительного A/B. `warm`: 30 с прогрева и 20 с записи, три повтора по умолчанию.
Диагностика использует full.
`--counts 0 1 8 32` задаёт нагрузки; `--variant Off|On|Tow` — выключенный мод, свободные тела или буксировка.
`--disable BodySpread BloodTrails` позволяет отдельно проверить отключаемые функции; применённые настройки входят в результат.
Полные команды и параметры остаются в [руководстве стенда](../tools/quick-test/README.md).

Не смешивайте холодные запуски, прогретую серию, короткий smoke-тест и профилировщик.
Профилирование добавляет расходы; вложенные inclusive-тайминги не суммируются.
Отсутствующая метрика не равна нулю. Для сравнения нужны одинаковые сцены,
настройки, исходники, прогрев и число повторов. Исходные JSON/CSV и ограничения
эксперимента сохраняются рядом с отчётом. Для просмотра используйте журнал или
[локальный дашборд](http://127.0.0.1:4178/), не создавая страницу на каждую правку.

## Выпуск

Перед сборкой сверить [статус выпусков и кандидата](RELEASE_STATUS.md). Не считать
рабочее дерево, замороженный снимок, установленный JAR и ZIP одной сборкой.
Исторические отчёты опубликованных releases/ не переписывать ради нового статуса.

1. Зафиксировать состав кандидата и проверить неизменяемый снимок.
2. Выполнить полный `check`; после изменений Java собрать JAR и сверить состав/хэши.
3. Проверить применимые игровые сценарии на копии мира: нагрузки, отвязку середины,
   сохранение и полный перезапуск, тела игроков, лут, оборудование и SP/MP.
4. Сохранить отдельный пакет в `releases/<версия>/`: ZIP, манифесты, SHA-256,
   результаты и ограничения проверок. Выпущенные пакеты задним числом не менять.
5. Публикация Workshop и обновление сервера — отдельно разрешаемые действия.
   При обновлении сервера сначала штатное сохранение/остановка и проверяемый бэкап
   полного мира, базы игроков и настроек, затем обновление и проверка запуска.

На сервере и клиентах нужны совместимые Lua/JAR, протокол и Lua checksum,
а также ZombieBuddy с Java-агентом. Проверенный запуск сервера не подтверждает
игровой вход и буксировку двумя клиентами.

## Дашборд и журнал

### Роли замеров в дашборде

В `local/runs/<серия>/plan.json` задавайте `dashboard.stages`: ключ — этап из журнала, значение — `{"role":"candidate|control|reference","buildId":"идентификатор замороженной сборки"}`. Контроль и ориентиры сохраняются в данных и парных сравнениях, но по умолчанию не входят в историю изменений. Неизвестная роль не считается подтверждённой новой сборкой; исходные записи не удаляются.

### Чтение сегментного профиля

Дашборд: экран «Профиль кода · архив rc1», источник `local/runs/rc1-segment-profile-20261101/{1,32}-Tow-1/profile.json`. Профиль 01.11 включает прогрев и торможение, один инструментированный цикл на число тел; не заменяет чистые FPS и не описывает последние изменения сборки.

- Нормализация: сумма времени / число вызовов `client.OnTick`; это мс на обновление, не количество пропущенных тиков. Вызовы/тик показывают кратность работы.
- Self исключает вложенные **измеренные** участки; неизмеренные дочерние вызовы остаются внутри него. Inclusive включает вложенные участки, складывать inclusive нельзя.
- Группировка по модулю позволяет выбирать функции, но не является восстановленным деревом вызовов. Для настоящего дерева нужны записанные связи родитель–потомок.
- В архиве на 32 телах: `presentation.update` self 2,232 мс/тик; `CVP_LinkSimulation.tick` self 1,680, inclusive 2,219; `CVP_LinkService.tick` self 0,376; `CVP_LinkRuntime.samples` self 0,289. На одном теле первые два self — 0,099 и 0,125 мс/тик. Это приоритеты исследования той сборки, не доказанный выигрыш будущих исправлений.
- Сначала сравнивайте одинаковый участок и режим измерения; общую цену игры, GPU, GC и JIT нельзя выводить из суммы этих Lua-сегментов. Исходные профили сохраняются отдельно от агрегатов дашборда.

Профили разных версий показываются отдельными сериями, а не объединённой временной линией. Автоматический прогон **`MP автопроверка.cmd`** (`tools/Run-MPAuto.ps1`) сам

Клиенты должны иметь тот же комплект Lua/JAR, ZombieBuddy и карту. M→2 не выполняет
сценарий сохранения/восстановления сам по себе. Стенд `tools/mp-test/mod` имеет
отдельную защиту удалённого полигона; его нельзя включать на новом сервере
простым обходом защиты. Автоматическая поездка не заменяет проверку границ
отмены/отключения/перезапуска — для них есть модельные тесты и отдельный живой
сценарий. Пользовательская ручная проверка 0.8.0 подтвердила обычную работу
двух клиентов, но не эти границы.

Живая MP-проверка нужна после изменений сетевых сообщений, владения физикой,
сопротивления, сохранений и перед выпуском с такими изменениями:
1. Сверить сборки сервера и двух клиентов, карту, настройки и журналы загрузки.
2. Проверить 1 и 32 тела: разгон, повороты, остановку, слабину и реальные препятствия.
3. Второй клиент наблюдает движение; проверить передачу управления и переподключение.
4. Проверить привязку/отмену/освобождение, количество материалов и лут до/после.
5. Сохранить и перезапустить тестовый сервер, проверить восстановление связей.
6. Сохранить отчёт с хешами и результатами; не смешивать с FPS-сериями SP.

снимок на прогон, длинная карта, запись её хешей и проверка 10 заголовков движка.
