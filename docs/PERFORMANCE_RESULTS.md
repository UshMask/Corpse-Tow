# Результаты производительности (11.11.2026)

Два разных уровня измерений; их нельзя смешивать.

## 1. Сеть: устранение лишних полных снимков (подтверждённое улучшение)

Измерение в изолированной модели обработчиков на реальных Lua-модулях
(`tests/test_mp_budget.py`, `Network` fixture, lupa Lua 5.1, фиксированное время).
Это проверка ветвления и стоимости Lua-обработки, **не FPS сервера** и не размер
реального пакета.

| Сценарий, 100 запросов | До: операций / снимков / ответов | После: операций / снимков / ответов |
|---|---:|---:|
| 100 повторов завершённого запроса | 1 / 100 / 100 | 1 / **0** / **7** |
| 100 неверных команд | 0 / 100 / 100 | 0 / **0** / **8** |
| 100 допустимых по форме, но отклонённых authority | 8 / 100 / 100 | 8 / **0** / **8** |

Устранённая работа: полный `S.capture()`, подготовка всех страниц и пакеты
`state`/`loads` на каждый повтор/отказ. Дополнительно бюджет ответов
`REPLY_MAX=8`, пополнение `0.008/мс` (8/с) ограничивает `result`-пакеты на спам;
успешные подтверждения операций не расходуют этот бюджет и ограничены отдельным
бюджетом операций. Повтор больше не сбрасывает `peer.heartbeat`/`visiblePages`,
поэтому не заставляет полный снимок; потерянное состояние восстанавливает
клиентский ограниченный `sync`. Счётчики:
`CVPMPServer.stats.{captures,publishes,results,rejected,rateLimited,duplicates,repliesDropped}`,
сброс `CVPMPServer.resetStats()`.

Воспроизведение:

```powershell
.venv/Scripts/python.exe -B tools/mp_budget_probe.py --json local/runs/mp-budget-after.json
.venv/Scripts/python.exe -B -m unittest discover -s tests -p "test_mp_budget.py" -v
.venv/Scripts/python.exe -B -m unittest discover -s tests -p "test_link_multiplayer.py" -v
```

До/после снято одним и тем же `tools/mp_budget_probe.py`; «до» — в отдельном
`git worktree` на `26bb716`, поэтому снимки и ответы не зависят от правок.

Ограничение: транспортная задержка, реальная сериализация PZ, потеря пакетов и
>2 клиентов здесь не моделируются; их проверяет живой MP-стенд.

## 1a. Нагрузка MP-сервера при 4/32/128 телах

`tools/mp_server_load.py`, тот же offline-обработчик, 3 повтора по 30 кадров
(`dt=100 мс`), прогрев 5 кадров, медиана ms на серверный тик. 4 тела — 1 цепь,
32 — 1 цепь, 128 — 4 разрешённые цепи по 32. «До» — `git worktree` на `26bb716`;
«после» — текущая ветка. Это стоимость Lua-обработчика, **не FPS**.

| Тел / связей | До, медиана (p95) | После, медиана (p95) |
|---|---:|---:|
| 4 / 4 | 0.971 (0.991) | 0.846 (0.864) |
| 32 / 32 | 6.163 (6.255) | 4.947 (5.176) |
| 128 / 128 | 21.323 (21.532) | 19.815 (20.134) |

Разница 4–18% получена не в изолированном A/B с чередованием, а последовательными
прогонами; повтор в обратном порядке дал близкие значения (32 тела: 5.33 против
5.49 мс), поэтому это **не** заявление об ускорении. Главное — отсутствие
регрессии на 4/32/128 и сохранение физики/рендера. Кандидаты оптимизации
решателя (`GroupConstraints.step`, `Obstacles.check`, `Core.advance`) остаются
следующим шагом; в этой итерации они не менялись.


## 2. Автономная матрица Lua-стоимости (диагностика, не FPS)

`tools/diagnostics_bench.py`, lupa Lua 5.1, Windows 10, 20 логических ядер,
3 повтора на сценарий (один из трёх часто +30% из-за шума ОС, используйте
медианы), прогрев указан в raw JSON. ms/кадр, медиана (p95):

| Сценарий | Медиана (p95) |
|---|---:|
| Без связей (idle authority) | 0.002 (0.002) |
| 4 тела | 0.478 (0.482) |
| 32 независимых связи | 3.434 (3.458) |
| Цепь 32 тела, прямая | 2.667 (3.490) |
| Цепь 32, поворот | 2.696 (2.702) |
| Цепь 32, торможение | 2.625 (3.440) |
| Цепь 32, назад | 46.472 (47.096) |
| Цепь 32, заблокировано | 0.788 (0.796) |
| 128 тел = 4×32 группы | 210.656 (220.531) |
| 128 тел, поворот | 265.676 (274.493) |
| Избыточные запросы | 2.755 (3.500) |
| Чанк недоступен | 0.411 (0.431) |
| Переподключение | 0.474 (0.511) |
| `save.flush` (модель фикстуры) | 1.858 (1.859) |
| Presentation 32-цепь | 3.133 (3.968) |
| Presentation 32-независимые | 4.929 (4.976) |
| MP: сервер 8 тел | 1.419 (2.200) |
| MP: клиент owner/friend | 0.005 (0.005) |

Горячие точки (inclusive, вложенные не суммировать): на 128 телах
`groupConstraints.step` ≈205.6 из 210.5 ms `sim.tick` (~97.6%), рост
сверхлинейный; на 32-цепи — 2.255 ms/кадр; `Obstacles.check` доминирует в
сценах многих независимых групп, `CVP_Core.advance` — в малых группах;
`presentation.update` на 32 независимых ≈1.43 ms, но большая часть — замоканные
нативные upload-вызовы, которые в игре считает Java/GPU.

**Оптимизация решателя не выполнялась.** Кандидаты (`GroupConstraints.step`,
`Obstacles.check`, `Core.advance`) требуют изменения физики/качества и находятся
вне безопасного подтверждённого выигрыша: измерения на 32/128 телах имеют
разброс до 30%, а кеширование поз/вызовов пересекает контракт «поза не
переиспользуется между коммитами». Оставлять спекулятивное усложнение без
подтверждённого выигрыша не стали; это зафиксировано как следующий шаг.

Воспроизведение:

```powershell
.venv/Scripts/python.exe -B tools/diagnostics_bench.py --phase baseline `
  --label diagnostics-20261111-baseline `
  --output local/runs/diagnostics-20261111-baseline --write-readme
```

Сырые данные и условия: `local/runs/diagnostics-20261111-baseline/`
(`raw-baseline.json`, `README.md`, `ANALYSIS.md`), `local/` не входит в Git.
Этот стенд не запускает PZ/Kahlua/JVM/Bullet/рендер; абсолютные значения не
являются FPS игры, сравнение осмысленно только для одинаковых прогонов на одной
машине. Игровые FPS-серии остаются в существующем журнале
`local/performance/` и выполняются отдельно по `docs/DEVELOPMENT.md`.
