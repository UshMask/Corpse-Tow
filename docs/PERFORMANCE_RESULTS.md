«0.8 / 5 / 20» были **миллисекундами на серверный Lua-тик** в offline-модели,
а не FPS и не стоимостью игрового решателя. Их нельзя сравнивать с FPS из
GPU-прогонов и нельзя выдавать за ускорение игры.

## 1. Что было не так со старым стендом

1. `scenario_list()` писал `reps`, а исполнители читали `repeats` — часть
   конфигураций фактически не использовала заявленное число повторов.
2. `__benchBatch()` возвращал среднее по серии; `summarize()` описывал
   распределение *средних*, а подписывался как p95/p99 кадров. Настоящих
   per-tick p50/p95/p99 не существовало.
3. `__benchSnapshot/__benchRestore` восстанавливали только позиции. Углы,
   скорости, `takeup`, история ограничений, траектории, часы и `Sim.records`
   могли переходить из повтора в повтор; `Sim.index=nil` не гарантировал
   пересборку.
4. MP-сценарий измерял сервер и клиентов длинными раздельными сериями без
   доставки пакетов. Клиент после `now-lastState>3000` прекращал обновление
   тел, то есть часть серии измеряла уже не рабочий путь.
5. 128 тел были четырьмя цепями в разных направлениях, 32 — одной прямой
   цепью: это разные геометрии, а не чистое масштабирование.

## 2. Исправленный стенд (схема v2)

- Единый ключ `repeats`; `scenario_repeats()` падает на отсутствующем/неверном
  значении; тест исполняет сценарий и проверяет фактическое число прогонов.
- Каждый повтор — **свежая VM/фикстура** с одинаковым seed/настройками/входом;
  сборка и прогрев вне измеряемого участка. Канонический хеш состояния до/после
  должен совпасть у всех повторов, иначе результат отклоняется.
- `batchMeanMs` — распределение средних серий; `tickMs` — настоящие per-tick
  сэмплы (p50/p95/p99, histogram, ограниченный `samplesMs`, `sampleStride`).
  Таймер один вызов на кадр; отдельно измерена его цена ~0.29–0.32 µs/тик.
  Внутрь `tether()` Python-таймер не ставился.
- MP: каждый кадр `server tick → доставка server→clients → client ticks →
  доставка clients→server`. Стоимость доставки входит в `frameMs` и отдельно
  публикуется `delivery`. Проверяются свежесть, реально обновлённые тела/строки,
  активные presentation-пути, продвижение sequence; одних `links` недостаточно.
  `mp.live`, `mp.idle`, `mp.loss` — отдельные сценарии.
- Матрица: `controlled-scaling` 1/2/4 одинаковые 32-цепи; `scaling-comparison`
  32 независимых крепления против одной 32-цепи; `stress` — поворот, торможение,
  задний ход, препятствия, смешанные направления 128 тел.
- Каждый результат содержит фактический backend (`lua-reference` в offline
  модели; `java-persistent`/`java-nonpersistent` для native), dt, подшаги,
  ожидаемый объём, хеши состояния и исходных файлов. Неверный backend,
  исчезнувшие тела, остановленная симуляция и недетерминизм отклоняются.

## 4. Java-решатель: одинаковые численные входы

Воспроизводимый harness на реальной Kahlua-фикстуре и реальном game JVM:

```powershell
.venv\Scripts\python.exe -B tools/solver_bench.py --label stage5-java-solver
```

Он компилирует текущий `CorpseProxyLab/source/**`, отдельно компилирует
замороженный baseline как `cvpworld.TowingSolverBaseline`, прогоняет 12
сценариев × 180 тиков, прогревает JVM, исключает прогрев из времени, считает
FNV-1a по IEEE-битам 17 полей тела + group/load и проверяет, что counters не
меняют физику.

## 5. Эквивалентность: три независимых сравнения

`tests/test_solver_equivalence.py` + `tests/ValidateSolverEquivalence.java`
сравнивают **старый Java / новый Java**, **старый Lua / новый Lua** и
**новый Java / новый Lua** в одном Kahlua JVM, с замороженным baseline.

Итог `local/runs/solver-equivalence-20261112-002054/report.json`:

- **1 551 505** сравнённых значений, **max absolute error = 0.0**,
  28/28 сценариев, 0 расхождений; tolerance 1e-13 не ослаблялся;
- JAR `74975747…A24768`, `cvpworld/TowingSolver.class` в JAR
  `4F68F1C7…C4958E8` совпадает с классом, скомпилированным из текущего

## 6. Решение по этапу 3 (кусочно-линейный поиск)

Ветка ограничения поворота действительно входит во внутренние 28 итераций:
0.19% вызовов на прямой 32-цепи и 5.34% на jump/gap-сценарии. Однако:

- измерена частота входа, но не выделена доля времени внутри 28 шагов;
- замена бисекции точным корнем меняет результат около порога сходимости,
  поэтому требует отдельного допуска и полного сравнения траекторий/сил;
- безопасное кэширование этапа 2 уже даёт 1.211× при **нулевом** численном
  расхождении; риск для игровой физики выше ожидаемого выигрыша.

Поэтому эксперимент **не включён в production** и отдельного коммита
«эксперимент» нет. Бисекция остаётся oracle; при появлении профиля,
показывающего существенную долю времени в этой ветке, эксперимент можно
повторить на отдельной ветке без блокировки текущих исправлений.

## 7. Что не измерено

- **Нет живого SP/MP-прогона** этой сборки: не запускались клиенты/сервер,
  реальное сохранение, WAN и два настоящих клиента.
- Нет in-game FPS. Для сравнения: предыдущая серия GPU-стенда (не эти
  изменения) при 8 телах, 1280×720, uncapped: driver 415.29 FPS mean /
  89.78 1% low, passenger 424.86 / 86.23 — отчёт
  `local/runs/immers-uncapped-8cpu16gb-rtx2080ti-20261111-8-bodies/fps-report.json`.
- Java-микробенчмарк меряет только численный решатель, не полный серверный
  тик и не FPS.
- Offline Lua-стенд не содержит native backend; `GroupConstraints`-Lua
  оптимизация проверена на Lua-модели, Java — отдельно на JVM.
- Быстрые и полные режимы стенда несравнимы; сравнивались только quick-quick.
- В MP-модели доставка — Python pump, потеря пакетов детерминированная,
  без jitter/reorder и реального транспорта.

## 8. Воспроизведение

```powershell
# Lua-стенд: одинаковый файл на базовом worktree и текущем дереве
.venv/Scripts/python.exe -B tools/diagnostics_bench.py --quick --no-mp `
  --expect-backend any --output local/runs/solver-bench-opt-a

# Java-решатель, baseline и текущий в одном JVM, реальная Kahlua-фикстура
.venv/Scripts/python.exe -B tools/solver_bench.py --label stage5-java-solver

# Три независимых сравнения + проверка JAR/class hash
.venv/Scripts/python.exe -B tests/test_solver_equivalence.py

# Официальная сборка/нативные проверки
powershell -NoProfile -ExecutionPolicy Bypass -File tools/Project.ps1 -Action build
```

Для базовой линии используется отдельный `git worktree` на `8106ddf`
(содержимое solver/Lua совпадает с `a892f58` после нормализации EOL).
Числа на другой машине/другом режиме не сравнивать с этой таблицей.
